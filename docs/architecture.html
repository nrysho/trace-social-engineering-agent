Architecture and persistence

An autonomous, bounded research-to-response loop. Each decision keeps its evidence; explicit pushback changes the next move. All contact stays inside the authorised AI-twin simulator, with no human message approval during scoring.

01 / RESEARCHProfile with sourcesOfficial target scope; sourced facts and hook hypotheses. Identity mismatch blocks. Thin corroboration warns.
02 / STRATEGY + WRITERChoose, explain, draftRank approaches once; retain rejected alternatives. Draft using facts, history, sender and session lessons.
03 / QUALITY + TRANSPORTCheck before contactMessages, pages and call turns pass rules. At most two corrections. Register pages; reuse stable retry keys.
04 / REACTION + EVIDENCERecord and interpretSave API receipts, touches and raw events. Evaluate the reply; close the branch with a typed reason.
Closed loop: reaction → observation + source contact → typed closure → session/target lesson → constrain the next ranked approach and inform the writer. Explicit stop requests end further contact.

When the recipient pushes back

  • Engagement: answer the question in the same story and progress the dialogue.
  • Doubt: address it once; persistent doubt closes the branch.
  • Silence: bounded follow-up; do not infer that the person never reads this channel.
  • Explicit rejection: preserve the quote and exclude the declined pretext family. Soft inferences remain tentative.
  • Stop request: stop the session, including later call turns and follow-ups.

Illustrative example: "Not interested in recruitment" closes that family. It does not prove "never reads email." This is a policy example, not a claimed scoring result.

When the system fails

  • Budget: ten touches in eval, synced to API cumulative counts. One acknowledged call costs one touch, up to ten turns.
  • Retry: preserve the original contact key and payload. Ambiguous session creation is not blindly repeated.
  • Unknown delivery: stop for reconciliation; do not pivot under a new key.
  • Partial call: save the acknowledged start and each successful turn before continuing.
  • Persistence: save branch closure before progression; keep lessons, tree decisions, QA verdicts and API journal for replay.

How the jury can replay the architecture

Sourced profile → chosen approach and rejected alternatives → exact checked content → API receipt and touch count → raw reaction → evaluator decision and closure → lesson that explains the next move. The read-only viewer and architecture evidence panel expose these records and flag missing links.

Trust boundary and limits. Draft is not contact; reply is not incident. Observed event → local candidate → official confirmation remain distinct. Source flags and domain checks do not prove truth or ownership. Full automatic used-session recovery is unfinished. Optional critic/identity/SQLite layers require explicit inputs.
